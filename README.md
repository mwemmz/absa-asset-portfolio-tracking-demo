# Lusaka 1 - Asset Portfolio Tracking

**SIMULATED DATA**

A working prototype of an asset portfolio tracking dashboard for a Zambian
construction and mining logistics company: 25 simulated trucks moving along real
Zambian road corridors, live map, incident management, a full audit trail, and
monthly fleet reports.

> Every vehicle position, driver, customer, incident and figure in this
> application is randomly generated by a simulation engine. Nothing here is
> connected to a real fleet, a real telematics provider, or any bank's systems,
> and it contains no customer data. The disclosure banner appears on every
> screen on purpose - please leave it in place.

---

## Requirements

- **Node.js 22.12+** (developed on v24) - `node --version`
- npm 9+

No database server, no Docker, no API keys. A local SQLite file is created and
seeded automatically on first run. If you would rather use Turso, see
[Using Turso](#using-turso) - it is the same SQL and the same code path.

## Quick start

```bash
npm install      # installs the client and server workspaces
npm run dev      # API on :4000, dashboard on :5173
```

Open <http://localhost:5173> and sign in:

| Role     | Email               | Password    | Can do                                     |
| -------- | ------------------- | ----------- | ------------------------------------------ |

| Monitor  | `monitor@lusaka1.io`| `lusaka1pw` | View and work alerts, but not reset        |

Both accounts are hard-coded on purpose: this is a self-contained prototype, so
do not reuse these credentials anywhere real.

### Screens

- **Dashboard** - fleet counters, alert feed, activity, uptime and asset-value tiles. Refreshes every 5 seconds.
- **Live map** - all 25 vehicles, geofences, planned corridors, click a truck to select it.
- **Vehicles** - searchable, filterable fleet list with status, device and driver.
- **Vehicle detail** - current state, asset and agreement details, telemetry, route history over 3/6/12/24 hours, a journey timeline, and that vehicle's alerts.
- **Alerts** - filter by status, type and severity; work the incident workflow; read the audit trail.
- **Report** - monthly fleet report with month-on-month comparison, print / Save-as-PDF ready.

## The simulation engine

`server/src/simulate.js` advances the whole fleet every **5 seconds**:

- vehicles move along their assigned corridor at plausible speeds and headings,
  and turn around at the end of a route;
- some go off-corridor and filter back, some stop for long periods, some lose
  comms, some go fully offline, some have their device tampered with;
- incidents raise alerts, and alerts auto-resolve when the condition clears;
- positions are pruned after 3 days.

Everything is driven by a seeded PRNG, so a reset reproduces the same scenario.
The first ten vehicles are primed to raise an incident within the first few
minutes so a short run always has a live alert feed.

**Road geometry is real.** Corridors follow actual OpenStreetMap road geometry
baked into `server/src/data/routes.json` from the public OSRM server, so
vehicles follow plausible Zambian roads rather than straight lines. The app
makes no network requests at runtime for routing or tiles; map tiles come from
openstreetmap.org and need an internet connection.

## Using Turso

The API speaks **libSQL**, so it runs against either a local SQLite file or a
remote [Turso](https://turso.tech) database with the same SQL and the same code
path. No Docker, no database server locally.

With no configuration it uses the local file `server/data/lusaka1.db`.

To use Turso, create a database and a token, then put both in `server/.env`:

```bash
npm install -g @turso/cli
turso db create lusaka1            # or use an existing database
turso db show lusaka1 --url        # -> libsql://lusaka1-xxxx.turso.io
turso db tokens create lusaka1     # -> eyJhbGci...
```

```bash
cp server/.env.example server/.env
```

```ini
TURSO_URL=libsql://lusaka1-xxxx.turso.io
TURSO_AUTH_TOKEN=eyJhbGci...
```

Then seed it once and start as usual:

```bash
npm run reset     # wipes and seeds whichever database TURSO_URL points at
npm run dev
```

`server/.env` is git-ignored. **Never commit the token.** `/api/health` reports
`driver: "turso"` once it is connected, which is the quickest way to confirm the
API is really talking to the remote database rather than the local file.

Notes for the remote case:

- Schema creation is handled on boot, so an empty database works; the server
  also seeds itself when it finds no vehicles.
- The API is not stateless-remote-friendly for high write rates: each simulation
  tick is one transaction that rewrites the fleet. Five-second ticks against one
  database are fine; do not point a second copy of the app at the same database
  at the same time.

## API

Base URL `http://localhost:4000/api`. Everything except `/api/health` and
`/api/login` needs `Authorization: Bearer <token>`.

| Method | Path | Purpose |
| ------ | ---- | ------- |
| GET  | `/health` | Liveness, simulation status, simulated-data notice |
| POST | `/login` | `{ email, password }` -> `{ token, user }` |
| GET  | `/me` | Current user |
| GET  | `/vehicles` | Fleet list; `?status` `?deviceStatus` `?routeId` `?q` |
| GET  | `/vehicles/:id` | Vehicle plus `recentAlerts` and `alertCounts` |
| GET  | `/vehicles/:id/history` | `?hours=1..168&limit` - positions oldest to newest |
| GET  | `/vehicles/:id/route` | Assigned corridor with drawable geometry |
| GET  | `/routes` | All corridors |
| GET  | `/geofences` | Monitored zones with polygons |
| GET  | `/alerts` | `?status` `?type` `?severity` `?vehicleId` `?from` `?to` `?limit` |
| GET  | `/alerts/summary` | Counts by status, type and open severity |
| GET  | `/alerts/audit/recent` | Newest audit events across all alerts |
| GET  | `/alerts/:id` | One alert plus its full `events` trail |
| PATCH | `/alerts/:id` | `{ status?, responseStatus?, note? }` |
| POST | `/alerts/:id/notes` | `{ note }` - append to the trail |
| GET  | `/stats` | Dashboard counters |
| GET  | `/stats/by-type` | Alert counts by type |
| GET  | `/reports/monthly` | `?month=YYYY-MM` |
| GET  | `/reports/months` | Months that contain data |
| POST | `/reset` | Admin only. Reseed and clear sessions |
| POST | `/tick` | Force one simulation tick |

Errors come back as `{ "error": "message", "details": ... }` with meaningful
status codes: `400` invalid input, `401` not signed in, `403` wrong role,
`404` unknown id or route, `409` illegal workflow transition.

### Incident workflow

Alert status only moves forward, and `resolved` is terminal:

```
new -> verified -> escalated -> resolved
  \_____________________________/   (resolved is reachable from any state)
```

Separately, the field response moves:
`not_required -> pending -> dispatched -> on_site -> closed` (with `stood_down`
available along the way). Both are written to `alert_events` with the actor,
their role, the time, and any note - nothing changes silently. Attempting an
illegal transition returns `409` with the list of allowed next states.

## Five-minute walkthrough script

1. **Reset first** (`npm run reset`, or Admin -> Reset data) so the story is
   reproducible. Sign in as `admin@lusaka1.io`.
2. **Dashboard, 30 seconds.** Point out the disclosure banner, then the fleet
   counters: 25 vehicles, how many moving/stopped/offline, open alerts, total
   portfolio value. Mention that the tiles update every 5 seconds.
3. **Live map, 60 seconds.** Zoom to the copperbelt corridor. Click a moving
   truck: driver, status, speed, corridor. Toggle a geofence layer and point at
   a mine or border zone. Say that the roads are real OpenStreetMap geometry
   and the vehicles are simulated.
4. **Vehicles -> one truck, 60 seconds.** Show search, the device-status filter,
   then open the detail page. Switch the history range 3h -> 24h, press **Fit**,
   and walk the journey timeline. Point out uptime, odometer and open alerts.
5. **Alerts, 90 seconds - the core of the prototype.** Filter to **New**.
   Open an alert. Walk the five-step workflow: **Verify alert** with a note,
   then **Escalate**, then move the response to **Team dispatched**. Add a note
   of your own. Watch every action appear in the audit trail with your name and
   the time. Then **Resolve** it and show that the trail is now read-only.
   Try an illegal move to show the guard rail if there is time.
6. **Report, 60 seconds.** Show the current month, the month-on-month block, the
   alerts-per-day chart, the type and severity breakdowns, and the vehicle
   table. Press **Print / Save PDF** to show the report is paper-ready.
7. **Close, 15 seconds.** Sign out, sign back in as `monitor@lusaka1.io` and
   show that the monitor role cannot reset the data. Remind the audience that
   every figure is simulated.

## Seeded scenario

`npm run reset` produces a known starting point: 2 users, 8 corridors, 5
geofences, 25 vehicles, 3600 position fixes, 342 historical alerts and 1527
audit events spread over the previous two months, so the report page has real
material to show. The previous month is complete; the current month is
month-to-date.

## Limitations - say these out loud

- Simulated data only. No telematics hardware, no carrier, no live GPS.
- Auth is an in-memory token with an 8-hour session. No password hashing beyond
  a seeded hash, no refresh tokens, no real user management.
- No write path for vehicles, routes or geofences; the fleet is fixed by seed.
- Route matching is "nearest point on the assigned corridor", not map matching,
  so deviation is a straight-line distance.
- Positions are pruned after 3 days, so long-range history is not available.
- The report is generated on request; there is no scheduled PDF export or email.
- Map tiles require internet access; everything else runs offline.

## Troubleshooting

| Symptom | Fix |
| ------- | --- |
| `Cannot reach the API` in the browser | The API is not running. `npm run dev:server`, check <http://localhost:4000/api/health> |
| Port 4000 or 5173 already in use | Stop the other process, or set `PORT` for the API / `--port` for Vite |
| Blank page, no data | Hard-refresh. If the API is up, `npm run reset` and reload |
| Map is grey with no tiles | No internet connection - tiles are from openstreetmap.org. Vehicles and geofences still render |
| "Your session has expired" | Sign in again. A reset also clears sessions |
| Database looks wrong | `npm run reset` rebuilds it from scratch |
| `TURSO_URL is set but TURSO_AUTH_TOKEN is empty` | Add the token to `server/.env`; `turso db tokens create <db-name>` |
| `SERVER_ERROR: Server returned HTTP status 400` from Turso | The token is invalid, expired, or was revoked. Issue a new one and restart |
| `/api/health` says `local-sqlite` but I expected Turso | `TURSO_URL` is not being read - check `server/.env` exists and has no stray quotes, and that the API was restarted after adding it |
| Changing React breaks the app | This repo pins a single React version via root `overrides` and `resolve.dedupe`; do not let two copies of React into `node_modules` |
